# 发布与部署

Flow2Spec 使用 GitHub Actions 分别处理持续集成、网站部署和 npm 正式发布。维护者不再直接修改或推送 `gh-pages`。

## 持续集成

`.github/workflows/ci.yml` 在 Pull Request 和 `main` 推送时执行：

- Node.js 18、20、22 下运行 CLI 测试与 npm 打包检查；
- Node.js 22 下安装网站依赖并构建 Astro 静态站点。

## 网站部署

`.github/workflows/deploy-pages.yml` 在 `main` 中的 `website/`、`docs/` 或部署工作流发生变化时触发，也支持在 Actions 页面手动执行。

仓库必须在 **Settings -> Pages -> Build and deployment** 中将 Source 设为 **GitHub Actions**。工作流构建 `website/dist`，通过官方 Pages artifact 发布，不再提交生成文件到 `gh-pages`。

## npm 正式发布

`.github/workflows/publish-npm.yml` 只在 GitHub Release 发布时触发。发布前依次校验：

1. Release 对应的提交属于 `main`；
2. Tag（`v3.3.0` 或 `V3.3.0`）与 `package.json` 版本一致；
3. CLI 测试通过；
4. `npm pack --dry-run` 通过。

全部通过后，工作流使用 npm Trusted Publishing（OIDC）执行带 provenance 的公开发布，不需要在 GitHub 保存长期 `NPM_TOKEN`。

首次启用时，在 npmjs.com 的 `@double-coding/flow2spec` 包设置中添加 GitHub Actions Trusted Publisher：

| 字段 | 值 |
| --- | --- |
| Organization or user | `double-coding-lab` |
| Repository | `Flow2Spec` |
| Workflow filename | `publish-npm.yml` |
| Environment | 留空 |

正式发布顺序：

1. 在分支中修改 `package.json` 版本并完成 PR；
2. PR 合并到 `main`；
3. 在合并提交上创建匹配版本的 Git Tag；
4. 基于该 Tag 创建并发布 GitHub Release；
5. 在 Actions 中确认 `Publish package to npm` 成功。

失败的发布不得通过修改同一版本重试；修复后递增版本，再创建新的 Tag 与 Release。
